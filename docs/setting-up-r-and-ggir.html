Setting Up R and GGIR

Prepare an auditable R/GGIR workspace and learn how one documented GGIR() call turns raw files into quality-control, activity, and sleep outputs.

Learning outcomes

By the end of this module, you should be able to:

  1. Prepare R/RStudio and a project-specific GGIR workspace.
  2. Describe GGIR’s six numbered processing/reporting parts.
  3. Adapt and pilot a documented GGIR() call using current parameter names.
  4. Preserve the configuration, software versions, and pilot evidence needed to reproduce a run.

Lesson 4.1

Install and Document the Software Environment

GGIR is an R package that processes raw accelerometer recordings into summaries that can support physical-activity, inactivity, sleep, and circadian-rhythm analyses. Use the central GGIR() function as the user-facing entry point; it coordinates the numbered parts of the pipeline.

Official software links:

  • R: https://cran.r-project.org/
  • RStudio: https://posit.co/download/rstudio-desktop/
  • GGIR documentation: https://wadpac.github.io/GGIR/
  • GGIR parameter reference: https://wadpac.github.io/GGIR/articles/GGIRParameters.html
  • GGIR CRAN page: https://cran.r-project.org/package=GGIR

Install GGIR in R:

install.packages("GGIR")

Before running GGIR, record:

  1. R version,
  2. GGIR version,
  3. time zone,
  4. device type and placement,
  5. input folder,
  6. output folder,
  7. operator,
  8. date of processing,
  9. approved protocol parameters.

Course example: Pelotas/UFPel cohort
Use a dedicated project folder with separate subfolders for raw .gt3x files, GGIR output, QC review, and Stata files. Keep the exact GGIR() call used for each processing run in a dated script, even when only one argument changes.

Three levels of guidance: Reproducibility, explicit time zones, and preserving source files are general principles. The behavior and defaults of GGIR parameters are software-version dependent. Thresholds, wear rules, sleep-log handling, and ID extraction are study decisions. Never copy the course values into a real study without checking all three levels.

Lesson 4.2

GGIR’s Six Numbered Parts

GGIR’s current documentation describes six sequential computational parts. The default mode = 1:5 runs the first five parts; part 6 is optional and is described in the parameter reference as under development. Do not request part 6 merely because it exists.

Part Current role in the official pipeline Practical implication
Part 1 Load data, assess signal quality, and store derived metrics such as ENMO for later parts. Changing raw-data or metric settings requires reconsidering downstream outputs.
Part 2 Assess basic data quality and describe data per day, file, and optional day segment. Produces person/day summaries and core QC material.
Part 3 Estimate rest periods used by part 4. Required when the analysis needs the later sleep classifications.
Part 4 Label rest periods as sleep and summarize sleep by night and recording. Produces cleaned and full sleep summaries with different purposes.
Part 5 Combine earlier information, classify sleep and physical-behavior categories, detect bouts, and produce day/person summaries. Threshold and bout settings become part of the analysis method and output names.
Part 6 Support analyses spanning the full recording, including selected co-analysis and circadian-rhythm functionality. Optional; use only for a pre-specified question and verify the installed version’s documentation.

Official source: See The GGIR pipeline. Output reports and milestone files are not interchangeable: milestone .RData files connect GGIR parts internally, while user-facing CSV, PNG, and PDF files are stored under results.

Lesson 4.3

Core GGIR Parameters

The values below form one coherent course/project configuration, not a recommendation for a particular population. It uses L40/M100/V400 throughout modules 4–8; these values also match the current GGIR defaults, but that coincidence does not make them universally valid. Replace the ID rule, time zone, protocol masking, thresholds, and sleep settings only after documenting the study rationale.

library(GGIR)

input_dir <- "03_ggir_input"
output_dir <- "04_ggir_output"

GGIR(
  datadir = input_dir,
  outputdir = output_dir,
  mode = 1:5,
  idloc = 1,                 # Teaching placeholder: verify against file names
  desiredtz = "America/Sao_Paulo",
  do.enmo = TRUE,
  data_masking_strategy = 1,
  hrs.del.start = 0,
  hrs.del.end = 0,
  maxdur = 0,
  qwindow = c(0, 24),
  mvpadur = c(1, 5, 10),     # Part 2 MVPA bout durations
  timethreshold = 5,
  anglethreshold = 5,
  def.noc.sleep = 1,
  threshold.lig = 40,
  threshold.mod = 100,
  threshold.vig = 400,
  boutcriter.mvpa = 0.8,
  boutcriter.in = 0.9,
  boutdur.mvpa = c(1, 5, 10),
  boutdur.in = 20,
  timewindow = c("MM", "WW"),
  visualreport = TRUE,
  old_visualreport = FALSE
)

idloc = 1 is only a visible placeholder in this template. Confirm how GGIR extracts IDs from the actual file names during the pilot and change it when needed. The example time zone is appropriate only when both device configuration and data collection occurred in that zone; consult configtz when they differed.

Parameter What it controls Decision to document
datadir Folder containing input accelerometer files, usually raw .gt3x for this course. Which batch/folder was processed.
outputdir Folder where GGIR writes results and reports. Where outputs are archived and reviewed.
mode Which GGIR parts to run; the documented default is 1:5. Why any parts were omitted, repeated, or extended to part 6.
idloc How participant IDs are extracted from input names. The filename pattern tested in the pilot and a uniqueness check.
desiredtz / configtz Time zone of the study and, when different, device configuration. Exact time-zone identifiers and daylight-saving implications.
do.enmo Whether to calculate ENMO, the raw acceleration metric used in many GGIR workflows. Which acceleration metric is reported.
data_masking_strategy How recording boundaries or selected study windows are masked. Why the chosen strategy fits the wear protocol.
hrs.del.start Hours removed from the start of each recording. Whether deployment artifacts or first-day behavior should be excluded.
hrs.del.end Hours removed from the end of each recording. Whether return/download periods should be excluded.
maxdur Maximum duration processed from each file; 0 lets GGIR use available data. Whether processing should be truncated to a study window.
qwindow Part 2 day segments; c(0, 24) requests the full 24-hour segment. Whether the analysis also needs pre-specified sub-day segments.
mvpadur Part 2 MVPA bout durations in minutes. Required durations and the Part 2 bout criterion.
timethreshold / anglethreshold Duration and angle-variability criteria used to identify sustained inactivity periods. Their scientific justification for the placement and population.
def.noc.sleep How the sleep window is obtained when a sleep-log entry is unavailable; a single integer invokes a built-in algorithm. Sleep-log availability and the fallback rule.
threshold.lig, threshold.mod, threshold.vig Part 5 cut-points applied to the selected acceleration metric. Source, unit, population, placement, and metric for the cut-point set.
boutcriter.mvpa / boutcriter.in Required fraction of a Part 5 bout meeting the MVPA or inactivity criterion. Fraction, allowed interruptions, and relationship to the epoch size.
boutdur.mvpa / boutdur.in Part 5 durations requested for MVPA and inactivity bouts. Durations and whether the resulting ranges match the analysis plan.
timewindow Part 5 windows: MM is midnight-to-midnight and WW is waking-to-waking. Which window defines each outcome.
visualreport / old_visualreport Store the current per-recording QC report and, separately, the legacy report. Keep the current QC report; do not use the legacy report for QC.

strategy is deprecated in favor of data_masking_strategy. mvpathreshold remains documented as a legacy Part 2 parameter; when it is not supplied, GGIR uses threshold.mod. If a study intentionally supplies mvpathreshold, document why the Part 2 threshold differs from—or matches—the Part 5 threshold.

The template deliberately does not pretend that GGIR’s inclusion settings and the course’s downstream valid-day rule are the same decision. Inspect the resolved values of includedaycrit and includedaycrit.part5, then document how they relate to the course/project ≥10-awake-hour rule. A day removed during GGIR processing cannot be restored by a later Stata rule.

See the official parameter reference and cut-point and bout guidance.

Lesson 4.4

Process Raw Files, Then Preserve the Run

Start with one representative pilot file. Confirm ID extraction, timestamps, output names, warnings, and runtime before processing a full batch. After running GGIR, do not delete the milestone folders or overwrite the evidence needed to reproduce the run. Save:

  1. the processing script,
  2. the generated config.csv,
  3. R/GGIR and dependency versions,
  4. the raw input inventory with checksums when feasible,
  5. output folders and a manifest of expected reports,
  6. warnings/errors,
  7. the run date, operator, and protocol version.

Capture the software environment after the pilot:

packageVersion("GGIR")
R.version.string
writeLines(capture.output(sessionInfo()), "04_ggir_output/sessionInfo.txt")

GGIR writes the most recent settings to config.csv in the output directory. On a repeated run, settings may be re-used from that file when they are no longer written explicitly in the function call. Therefore, archive each approved configuration and use a new run directory—or deliberately manage configfile and overwrite—rather than assuming that deleting one line restores a default.

Mini-activity: build a pilot manifest
For one non-sensitive test file, record the input filename, extracted ID, device placement, configured and study time zones, GGIR/R versions, script name, output directory, cut-points, bout durations, sleep fallback, warnings, and reviewer. Then compare the generated config.csv with the script. Resolve every unexplained difference before a batch run.

Completion evidence: retain the dated script, manifest, config.csv, and sessionInfo.txt together. A second team member should be able to state which values are general software settings and which are study-specific decisions.

Practice

Self-check with Feedback

Check 1: You need standard day/person physical-activity and sleep summaries, but no full-recording co-analysis. Should you automatically use mode = 1:6?

Answer: No. Start with mode = 1:5 unless part 6 answers a pre-specified question. Part 6 is optional and its behavior must be checked in the installed GGIR version.

Check 2: You remove threshold.mod = 100 from a repeated script, but leave the prior config.csv in the output directory. Can you assume GGIR will use the current default?

Answer: No. GGIR can retrieve a prior setting from config.csv. Inspect the resolved configuration and archive it with the run.

Check 3: Which settings in the teaching call require a study-specific justification?

Answer: At minimum: ID extraction, time zones, masking, cut-points, bout durations/criteria, sleep-log fallback, and requested time windows. A valid R function argument is not automatically a valid scientific choice.

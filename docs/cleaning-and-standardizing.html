Module 6

Cleaning and Standardizing

Turn many GGIR output files into a documented set of variables that can be merged, filtered, analyzed, and audited consistently.

Output files Sleep cleaning Data dictionary

Learning outcomes

By the end of this module, you should be able to:

  1. Identify the main GGIR output files used for day, night, and person-level cleaning.
  2. Decode common GGIR part 5 file names.
  3. Use GGIR’s cleaned and full sleep outputs for their intended purposes.
  4. Determine whether required bout variables already exist before deriving anything downstream.
  5. Build a data dictionary and merge plan that preserve source, unit, and observation level.

Lesson 6.1

Know the Real GGIR Output Files

The exact files depend on GGIR version and options. Match the installed run to config.csv and the official output dictionary instead of selecting files only by a familiar-looking name.

Current output pattern Unit of observation Typical use
results/part2_summary.csv Recording/file Recording duration, calibration, clipping, coverage, and processing summaries.
results/part2_daysummary.csv Recording-day Day-level valid hours, timing, activity, and quality fields.
results/part4_nightsummary_sleep_cleaned.csv Recording-night Nights retained by GGIR’s configured sleep-cleaning logic; usual starting point for sleep analysis.
results/QC/part4_nightsummary_sleep_full.csv Recording-night Full diagnostic sleep output, including fields used to understand exclusions; use for QC rather than silently replacing the cleaned file.
results/part5_daysummary_WW_L40M100V400_T5A5.csv Recording-day window Day-level sleep/physical-behavior classifications for the course/project window and settings.
results/part5_personsummary_WW_L40M100V400_T5A5.csv Recording/file Person-level aggregates derived from the corresponding Part 5 day summary.

Before cleaning, test the unit of observation with the intended key. A day-level file can legitimately repeat participant IDs; a person/recording-level file should not repeat its intended recording key. A common mistake is joining person-level and day-level files without first deciding whether the result should remain one row per day or one row per person.

Course example: Pelotas/UFPel cohort
Treat GGIR outputs as structured evidence: keep part 2, part 4, and part 5 files in their original output folders; copy only the files needed for cleaning into the Stata working folder. Keep a record of which lot or processing batch each file came from.

Lesson 6.2

Decode GGIR File Names

GGIR file names often encode the cut-points and thresholds used. For example:

part5_personsummary_WW_L40M100V400_T5A5.csv

Read this as:

Segment Meaning
part5_personsummary Participant-level summary from part 5.
WW Waking-to-waking Part 5 time window.
L40 Light-intensity threshold/cut-point = 40.
M100 Moderate-intensity threshold/cut-point = 100.
V400 Vigorous-intensity threshold/cut-point = 400.
T5 Sustained-inactivity timethreshold = 5 minutes.
A5 Sustained-inactivity anglethreshold = 5 degrees.

The values in a file name are not decoration; they are part of the analysis method. If two files differ only in L/M/V, T, or A, they are different processing outputs. MM, WW, and OO also represent different Part 5 windows—midnight-to-midnight, waking-to-waking, and sleep-onset-to-sleep-onset, respectively. Never rename two configurations to the same generic filename.

Lesson 6.3

Sleep Cleaning

Current GGIR output already separates Part 4 night summaries into a cleaned analysis file and a full diagnostic file:

  1. Start analysis preparation from results/part4_nightsummary_sleep_cleaned.csv.
  2. Use results/QC/part4_nightsummary_sleep_full.csv to understand why nights were not retained and to investigate fields such as cleaningcode, sleeplog_used, fraction_night_invalid, error_onset, and error_wake.
  3. Confirm the intended recording ID, night, and calendardate keys before any merge.
  4. Compare the number of rows and recording IDs in the cleaned and full files and document the difference.
  5. Apply an additional exclusion only when it is pre-specified and supported by the installed version’s output dictionary or a study-maintained codebook.

No unsupported code deletion: Do not write drop if cleaningcode >= 2 or “drop codes 2–6” merely because those numbers appeared in an earlier script. The official GGIR sleep documentation explains that cleaned-output logic depends on whether a sleep log was proposed and used. If the Pelotas/UFPel pipeline has an additional numbered-code rule, retain it only after the project codebook names the variable, defines every relevant code, identifies the GGIR version, and records the scientific rationale.

See the official sleep-analysis guidance and Part 4 output dictionary.

Lesson 6.4

Use GGIR Bout Outputs Before Deriving New Ones

Current GGIR can calculate MVPA bouts directly:

  • Part 2 uses mvpadur with mvpathreshold (or threshold.mod when the legacy mvpathreshold is not supplied).
  • Part 5 uses boutdur.mvpa for MVPA bouts and boutdur.in for inactivity bouts, together with the corresponding bout-criterion parameters.
  • The teaching configuration requests 1-, 5-, and 10-minute MVPA bout durations and a 20-minute inactivity bout duration.

First search the matching Part 2 or Part 5 data dictionary and column names. Derive a downstream variable only if the required construct is absent or intentionally differs from GGIR’s definition. When a Stata derivation is necessary, name it so it cannot be confused with a GGIR field, and document:

  1. source resolution and acceleration metric,
  2. threshold and unit,
  3. bout duration,
  4. permitted fraction or interruption rule,
  5. treatment of missing/non-wear time,
  6. agreement check against an available GGIR result.

GGIR calls the lowest intensity category inactivity, not sedentary behavior, because posture is not necessarily classified. See the official bout guidance.

Lesson 6.5

Standardize Variable Names

Build a data dictionary that states:

  1. original variable name,
  2. standardized variable name,
  3. source file,
  4. unit of observation,
  5. merge keys,
  6. unit of measurement,
  7. original GGIR parameter/configuration,
  8. transformation and code version,
  9. missing-value rule,
  10. reason for exclusion or retention.

Before writing merge code, complete an inventory like this:

part2_summary.csv One row per recording To verify Record after import Pass/fail Recording-level QC
part2_daysummary.csv One row per recording-day To verify Record after import Pass/fail Day-level coverage
part4_nightsummary_sleep_cleaned.csv One row per recording-night To verify Record after import Pass/fail Cleaned sleep outcomes

Quick summary Review aid

Identify the participant-, day-, and night-level GGIR outputs before merging, and read thresholds encoded in part 5 file names as part of the analysis method. Apply only approved sleep and bout rules, then standardize variables in a data dictionary that preserves source, unit, transformation, and missing-value decisions.

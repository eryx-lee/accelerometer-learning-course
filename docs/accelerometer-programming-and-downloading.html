Module 2

Programming and Downloading

Move from study design to careful device initialization, complete download records, and traceable raw data handoff.

30–45 minutes ActiLife demonstration Download audit trail

Module guide: The concept route uses the checklists and self-check only. For the hands-on route, bring an approved study protocol, a compatible practice device, ActiLife access, a device-assignment log, and an approved raw-data location. Never practice with identifiable participant data. Your deliverable is a reconciled initialization/download log. You are finished when every device is linked to a participant or practice ID, an expected file, a storage location, and a documented exception status.

Learning outcomes

By the end of this module, you should be able to:

  1. Initialize an ActiGraph device using a documented protocol.
  2. Download recordings into reproducible folders and separate complete from incomplete collections.
  3. Explain the difference between raw .gt3x files and epoch-level .agd files.
  4. Record valid-day rules before data processing begins.

Lesson 2.1

Before Initialization

Before initializing a device, confirm the study identifier, device identifier, planned wear location, start and stop schedule, sampling settings, participant instructions, and the operator responsible for programming. Use a pre-deployment checklist so each device is initialized consistently.

Valid day means a participant-day that meets the study’s minimum data rule. In this course example, a valid participant record requires ≥4 valid days, ≥10 hours of awake wear per valid day, and at least 1 weekend day. These rules are common in physical-activity epidemiology, but they must be approved for each study population, protocol, and placement.

Protocol review required: Sampling frequency, start/stop times, participant identifiers, and initialization settings must come from the approved study protocol. Do not reuse settings from another cohort without review.

Mini-activity: pre-deployment check

Create one practice row with these fields: study ID, device serial number, exact model, firmware, ActiLife version, wear location, sampling setting, start/stop schedule, operator, and protocol version.

Check your row

A usable row identifies both the participant assignment and the technical configuration. If another operator could not reproduce the setup or determine which approved protocol was followed, add the missing field before initialization.

Lesson 2.2

ActiLife Initialization Workflow

Use the checklist below with the approved protocol. Menu labels can change between ActiLife versions, so record the software version and confirm the current manufacturer documentation before programming study devices.

  1. Open ActiLife and connect the device.
  2. Select Initialize.
  3. Choose Regular Initialization.
  4. Enter Subject Info using the study-approved participant ID and device assignment.
  5. Use clear only when the protocol confirms the device should be reset before deployment.
  6. Click Initialize 1 device.
  7. Record the initialization date, operator, device serial number, participant ID, planned wear period, and any issues in the deployment log.

Worked example: Pelotas/UFPel cohort
Use ActiGraph as the running example. Participant IDs, device serial numbers, start/stop dates, wear location, and operator initials should be logged before monitors leave the lab. This example illustrates a reproducible workflow; your own study must decide placement, sampling frequency, wear duration, and valid-day rules before initialization.

Quick summary Brief review

Use a study-approved checklist to initialize each ActiGraph device and log the participant ID, device serial number, schedule, placement, operator, and any issues. After return, download files to the approved raw-data folder, verify them against the deployment log, and document first-pass COMPLETE or INCOMPLETE triage.

Privacy correction shown in the video: Use Clear only when the approved protocol requires existing subject information to be reset. Enter only the study-approved coded participant ID; do not enter a participant name or other direct identifier. The corrected edition covers the unsafe placeholder shown in the legacy interface.

Lesson 2.3

Download Workflow

When devices return, download them before making cleaning decisions. A good download log records the date, device identifier, participant identifier, operator, file location, and comments about return status or participant-reported issues.

Recommended ActiLife download steps:

  1. Connect returned devices.
  2. Use Change location to point downloads to the approved raw-data folder.
  3. Select 5-Second Epoch when creating count-based .agd summaries for the ActiLife review workflow.
  4. Click Download all devices.
  5. Check that each expected participant has a file and that file names match the deployment log.
  6. Move files into COMPLETE or INCOMPLETE folders according to the rule below.

Complete / Incomplete Folder Rule

Create two top-level folders inside each download batch:

Folder Use when…
COMPLETE The device appears to contain at least half of the planned recording period and can proceed to standard processing/QC.
INCOMPLETE The device contains less than half of the planned collection time, is missing expected dates, or has a download/device issue that requires review before processing.

The “less than half of planned collection time” rule is an operational triage rule. It does not replace the final valid-day rule of ≥4 days, ≥10 hours of awake wear, and ≥1 weekend day.

Mini-activity: reconcile a returned batch

Imagine that 12 devices were assigned, 11 were returned, and 10 expected raw files were downloaded. Create a four-column exception list: device or participant ID, expected status, observed status, and next action.

Feedback

The batch is not reconciled until the missing device and the returned device without an expected file are both identified. Appropriate next actions might include contacting the field team, retrying a documented download, checking the assignment log, or escalating a hardware issue. Do not invent a file or silently mark the participant invalid.

Lesson 2.4

Raw Files, Epochs, and Why Both May Appear

Raw data are high-frequency acceleration samples stored by the monitor. For ActiGraph workflows, the raw recording is commonly exported or retained as .gt3x.

An epoch is a fixed time window used to summarize data. The demonstrated workflow creates a 10-second epoch .agd file for ActiLife review. It is count-based and is not the same as the raw .gt3x file used by GGIR in Module 4. A different study may specify a different epoch length.

The distinction matters:

File type What it represents Typical role in this course
.gt3x Raw ActiGraph acceleration data Main input for GGIR processing.
.agd with 10-second epoch Count-based ActiLife epoch summary used in this demonstration Useful for ActiLife review, quick checks, and some legacy workflows; follow the approved protocol if it specifies another epoch.
.csv Open text format exported from raw or processed files Used only when the downstream pipeline requires it.

Do not mix formats silently: If a report or script uses .agd counts, document that it is epoch/count based. If GGIR processes .gt3x, document the raw-data pipeline separately.

Wrap-up

Self-Check

  1. A returned device contains only three of seven planned days. Should it be deleted immediately?
  2. Which ActiGraph file type is the raw-data input for the GGIR workflow introduced later in the course?
  3. Why should the initialization log record the exact software and firmware versions?
  4. How does the COMPLETE/INCOMPLETE triage rule differ from the final valid-day rule?
Feedback and suggested answers
  1. No. Place it in the documented exception or INCOMPLETE path for review. Preserve the raw file and record the reason; final inclusion is decided after the approved quality rules are applied.
  2. The raw .gt3x file.
  3. Menus, defaults, supported hardware, and exported files can change. Version records make the setup interpretable and reproducible.
  4. Triage controls the operational handoff after download. The valid-day rule is an analytical eligibility rule applied after the relevant wear and quality measures are available.

Lesson 7.1

Final-Dataset Workflow

The video introduces an 11-step Stata plan. The web lesson expands that plan into the following 13-step checklist so that source freezing and target-grain decisions are explicit:

  1. Freeze the inputs: copy only approved source files into a dated, read-only analysis-input folder and preserve their original names/checksums.
  2. Import and label provenance: record the GGIR run, source filename, threshold configuration, time window, batch, and import date.
  3. Normalize IDs without destroying the originals: keep id_source, create one documented standardized ID, and verify unexpected truncation, leading zeros, and duplicates.
  4. Assert each source grain: use isid on the intended key before append or merge; stop when it fails.
  5. Append like with like: append batches only when variable definitions and GGIR configurations agree; retain a batch/source indicator.
  6. Choose the target grain: decide whether the working dataset is one row per recording-day, recording-night, or participant before combining levels.
  7. Merge with an explicit relationship: use the correct one-to-one, many-to-one, or one-to-many key and inspect every _merge category.
  8. Use the cleaned Part 4 sleep output by default: consult the full QC file to explain exclusions; do not delete unexplained numeric codes.
  9. Reuse configured GGIR bouts when they match the estimand: derive Stata bouts only when the required definition is absent or intentionally different.
  10. Create day-level eligibility fields: implement the pre-specified wear, day-boundary, and weekend definitions; validate them before aggregation.
  11. Aggregate once, transparently: produce the pre-specified participant summary while retaining an auditable day-level dataset.
  12. Apply eligibility without erasing evidence: create reason-specific flags, report overlaps, and save the pre-exclusion dataset before restricting the analytic sample.
  13. Save dated outputs and logs: include the final .dta, do-file, dictionary, merge/exclusion audit, README, and Stata log.

Course example: Pelotas/UFPel cohort
The UFPel do-file workflow should be credited to Otavio Leão, Giulia Salaberry, and Charles Lucena. Treat it as a strong reproducible example, not a universal template: your study must decide its own ID cleaning, valid-day rules, bout definitions, and exclusion criteria.

A minimal merge skeleton makes the checks executable. Replace every uppercase placeholder and inspect unmatched rows before allowing the script to continue:

version 18
clear all
capture log close
log using "logs/final_dataset_YYYYMMDD.smcl", replace

* Person/recording-level source
import delimited using "inputs/PERSON_FILE.csv", varnames(1) clear
clonevar id_source = ID
rename ID participant_id
isid participant_id
tempfile person
save `person'

* Day-level source
import delimited using "inputs/DAY_FILE.csv", varnames(1) clear
rename ID participant_id
rename CALENDAR_DATE calendar_date
isid participant_id calendar_date

* Target remains one row per participant-day: many days to one person row
merge m:1 participant_id using `person'
tabulate _merge, missing
assert _merge == 3
drop _merge

isid participant_id calendar_date
compress
save "working/day_level_pre_exclusion_YYYYMMDD.dta", replace
log close

assert _merge == 3 is appropriate only after the team has confirmed that no unmatched records are expected. If an unmatched category is legitimate, replace the assertion with a documented expectation and export the affected IDs for review.

Lesson 7.2

Spearman-Brown Prophecy Reliability

The Spearman–Brown prophecy formula projects how reliability would change if the number of comparable repeated measurements changed:

\[ r_k = \frac{k r_1}{1 + (k - 1)r_1} \]

where \(r_1\) is the estimated reliability at the baseline measurement length and \(k\) is the ratio of the proposed length to that baseline. In an accelerometer context, the repeated measurements may be valid days, but the projection is meaningful only when the reliability estimate and assumptions fit that use.

A defensible workflow is:

  1. pre-specify the outcome and which days/segments are considered comparable,
  2. estimate the baseline reliability with a method appropriate to the data structure,
  3. state the value of \(r_1\), the baseline number of days, and the proposed value of \(k\),
  4. calculate and report the projection with uncertainty or sensitivity analyses where appropriate,
  5. consider participant burden, selection bias, weekday/weekend representation, and missingness alongside reliability.

The formula does not prove that days are exchangeable, correct for systematic weekday/weekend differences, or validate a minimum-day cutoff by itself. Use it as one measurement-quality input, not as an automatic exclusion command.

Lesson 7.3

Three-Parameter Exclusion Rule

For the Pelotas/UFPel course example, final inclusion is evaluated using three parameters:

Parameter Example rule
Number of valid days ≥4 valid days
Awake wear duration ≥10 hours awake wear per valid day
Weekend coverage At least 1 weekend day

Keep the exclusion log. It should report how many participants were excluded by each rule, how many failed multiple rules, and the final analytic sample.

Study-specific rule: The ≥4-day, ≥10-hour, ≥1-weekend-day combination is an example protocol rule, not a GGIR default. Define “awake wear,” valid-day boundaries, weekend days, and missing values before coding. Do not use the recording-level complete_24hcycle score as a day-level inclusion flag.

One transparent Stata pattern is to create separate flags before a combined flag. Replace the placeholder field names only after checking their units and formats:

* Requires calendar_date to be a Stata daily date and awake_wear_hours in hours
generate byte valid_day_example = awake_wear_hours >= 10 ///
    if !missing(awake_wear_hours)
generate byte weekend = inlist(dow(calendar_date), 0, 6) ///
    if !missing(calendar_date)

bysort participant_id: egen n_valid_days = total(valid_day_example)
bysort participant_id: egen n_valid_weekend = ///
    total(valid_day_example == 1 & weekend == 1)

generate byte fail_n_days = n_valid_days < 4 if !missing(n_valid_days)
generate byte fail_weekend = n_valid_weekend < 1 if !missing(n_valid_weekend)
generate byte eligible_example = fail_n_days == 0 & fail_weekend == 0

tabulate fail_n_days fail_weekend, missing
tabulate eligible_example, missing

Here the ≥10-hour criterion defines valid_day_example, so a separate participant-level “fail 10 hours” flag would double-count the same rule. If the actual protocol defines three independent participant-level conditions, encode and label each condition exactly as written in that protocol.

Lesson 7.4

Save Final Outputs

Final outputs should include:

  1. immutable pre-exclusion day/night dataset,
  2. dated analysis-ready .dta file,
  3. data dictionary with source and transformation lineage,
  4. merge audit and unmatched-ID files,
  5. reason-specific exclusion table with overlapping failures,
  6. executable Stata do-file and run log,
  7. README with source GGIR configuration, batch dates, Stata version, and row/ID counts.

Example file name:

accelerometer_final_analysis_YYYYMMDD.dta

Avoid labeling a file final_final.dta or silently replacing a published dataset. If a result changes, create a new dated/versioned release and record why.
